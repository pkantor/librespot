# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

librespot — an open source Spotify client library and headless Spotify Connect receiver, written in Rust. Cargo workspace: the root package `librespot` is both a library (`src/lib.rs`, re-exporting all sub-crates) and the `librespot` binary (`src/main.rs`). Premium accounts only.

This checkout is a fork on branch `API`, tracking upstream via `dev`/`dev_org`. The fork adds two things upstream has no equivalent of: a TCP control API (`src/server.rs`) and an AirPlay receiver (`airplay/`). See "Fork-specific code" below.

## Commands

```bash
cargo build                     # default features: native-tls + rodio-backend + with-libmdns + airplay-remote-control
cargo build --release
cargo run -- -n "Librespot" -b 320 -c ./cache   # run the receiver
cargo test --workspace
cargo test -p librespot-core spotify_uri        # single test / filter
cargo run --example play "$ACCESS_TOKEN" 2WUy2Uywcj5cP0IXQagO3z
cargo run --package librespot-oauth --example oauth_sync   # obtain an access token for examples
cargo fmt --all
cargo clippy
./test.sh                       # full CI-equivalent run; note it runs `cargo clean` on entry and exit
```

`--no-default-features` alone fails to compile: at least one TLS backend must be selected, and the three TLS features are mutually exclusive (enforced by compile-time checks in `oauth/src/lib.rs`, which is compiled first in the dependency tree). Example:

```bash
cargo build --no-default-features --features "rustls-tls-native-roots alsa-backend with-libmdns"
```

All features are documented inline in the root `Cargo.toml`; platform dependencies are in `COMPILING.md`.

CI (`.github/workflows/quality.yml`) runs with `RUSTFLAGS: -D warnings` and uses `cargo-hack` to check every feature combination once per TLS backend:

```bash
cargo hack clippy -p librespot-protocol --each-feature
cargo hack clippy -p librespot --each-feature --exclude-all-features \
  --include-features native-tls --exclude-features rustls-tls-native-roots,rustls-tls-webpki-roots
```

Toolchain is pinned via `rust-toolchain.toml` (rustfmt + clippy components); MSRV 1.85, edition 2024.

The `channel = "1.97.1"` line in that file is **fork-local** — upstream ships no channel, which leaves the compiler floating: CI installs `dtolnay/rust-toolchain@stable` while contributors have whatever they have. That is not theoretical. 1.98.0 landed on 2026-08-18 and its wider `clippy::needless_late_init` fired on upstream code in `src/main.rs` untouched since 2025-08-13; with `-D warnings` that failed `quality`, and `rpi-release` is gated on it, so a lint from outside this repo blocked deploying to the Pi. The pin closes that: `dtolnay/rust-toolchain` only calls `rustup default`, never `rustup override set` and never sets `RUSTUP_TOOLCHAIN`, so the file wins in CI too and no workflow change is needed (verified by setting the local default to 1.98.0 and watching the directory still resolve to 1.97.1). Expect a conflict here on the next upstream merge — that is the moment to drop or bump it, which is the point. The file's own comment says how.

Two consequences worth knowing when a lint report doesn't match what you see: a *newer* clippy than the pin will find things the pin hides, so reproduce CI failures with `cargo +<version> clippy` rather than doubting the report; and `cargo clippy` re-emits nothing for a crate it did not rebuild, so a second run over an unchanged tree prints a bare `Finished` and looks clean whatever it said the first time — `touch` the files or `cargo clean -p librespot` before believing a green run.

Non-negligible changes need an entry in the "Unreleased" section of `CHANGELOG.md`, marked `(breaking)` if downstream crates must change to keep compiling (see `CONTRIBUTING.md`).

## Architecture

Crates layer strictly bottom-up; `librespot-core` is the foundation everything else builds on.

- **`protocol/`** — Spotify protobufs. `build.rs` compiles `proto/*.proto` into `OUT_DIR` at build time; the generated modules are not checked in. `src/impl_trait/` holds hand-written trait impls layered on the generated types.
- **`core/`** — session, transport, and all Spotify service clients:
  - `session.rs` — `Session` is an `Arc`-wrapped handle owning every subsystem and the mutable per-connection user data (country, attributes, client id/name, connection id). Everything downstream takes a `Session` and clones it.
  - `component.rs` — the `component!` macro. Every manager (`MercuryManager`, `AudioKeyManager`, `ChannelManager`, `DealerManager`, …) is a `(SessionWeak, Mutex<Inner>)` pair generated by this macro, using a weak session ref to avoid cycles. New session subsystems should follow this pattern.
  - `connection/` + `packet.rs` — the legacy TCP protocol to an access point: Diffie-Hellman handshake, Shannon-encrypted framed packets. Documented in `docs/connection.md`.
  - `dealer/` — WebSocket connection that carries Connect state updates and remote commands. Two payload shapes (protobuf messages and JSON requests); the JSON request models live in `core/src/dealer/protocol/request.rs` because the shipped protobuf definitions don't match. See `docs/dealer.md`.
  - `spclient.rs`, `login5.rs`, `token.rs`, `http_client.rs`, `apresolve.rs`, `cdn_url.rs` — the modern HTTP/gRPC-ish surface: access point resolution, login5 auth, token provisioning, metadata and CDN URL fetching.
  - `error.rs` — one crate-wide `Error { kind, error }` with gRPC-style `ErrorKind`s and constructors (`Error::unavailable(e)`, `Error::failed_precondition(e)`, …). Component-local error enums (e.g. `AudioFileError`) define `From` impls that map into the right `ErrorKind`. Follow this when adding errors.
  - `spotify_id.rs` / `spotify_uri.rs` — `SpotifyId` (raw 128-bit id) vs `SpotifyUri` (typed URI incl. named/local/playlist forms). These carry the crate's only substantial unit tests.
- **`metadata/`** — typed wrappers over the metadata protobufs (track, album, artist, episode, show, playlist, lyrics) fetched through `SpClient`. `metadata/src/audio/` defines `AudioItem`/`UniqueFields`, the normalized "thing to play" that the player consumes.
- **`audio/`** — encrypted audio file streaming: `fetch/` downloads via CDN with range requests (`range_set.rs` tracks what's downloaded, backed by a temp file, with separate "initial chunk" and "streaming" modes), `decrypt.rs` AES-CTR decrypts with the audio key from `core`.
- **`playback/`** — the playback pipeline: `player.rs` (the big one — track loading, decoding thread, normalisation, preloading of the next track, seek, and the `PlayerEvent` stream), `decoder/` (Symphonia, or `passthrough_decoder` behind a feature), `audio_backend/` (one file per sink: rodio, alsa, pulseaudio, jack, gstreamer, portaudio, sdl, pipe, subprocess — all implement the same `Sink` trait and register in `mod.rs`), `mixer/` (softmixer / alsamixer + volume `mappings.rs`), `convert.rs`/`dither.rs` for sample format conversion.
- **`connect/`** — Spotify Connect device behaviour on top of `core` + `playback`:
  - `spirc.rs` — the event loop wiring dealer messages, player events, and the public `Spirc` handle (`play`, `pause`, `next`, `set_volume`, `load`, `transfer`, `shutdown`, …). Commands are sent over a channel to the loop task; `Spirc::new` returns the handle plus a future you must spawn.
  - `state.rs` + `state/` — `ConnectState`, the mirrored player state published to Spotify. Split by concern: `context.rs`/`tracks.rs`/`provider.rs` (track list and where tracks came from), `options.rs` (shuffle/repeat), `transfer.rs` (taking over playback from another device), `handle.rs` (command handlers), `restrictions.rs`, `metadata.rs`.
  - `context_resolver.rs` — resolves and pages context URIs (playlists, albums, autoplay) into concrete tracks.
- **`discovery/`** — zeroconf advertisement and the local HTTP `addUser` endpoint that lets a phone hand credentials to this device. Three mutually exclusive mDNS backends (libmdns, avahi, dns-sd).
- **`airplay/`** — fork-local AirPlay receiver; see "Fork-specific code" below. Depends on `core` and `playback` only, and nothing depends on it but the binary.
- **`oauth/`** — standalone OAuth code flow with a loopback redirect; the modern way to obtain credentials, used by `main.rs` and the examples.
- **`cache/`** — credential and audio file cache on disk.

Authentication paths (`docs/authentication.md`): cached credentials → discovery/zeroconf → OAuth. `main.rs` reconnects on session loss with a rate limit (5 reconnects per 10 minutes) and re-creates the `Spirc` each time; the `Player` outlives sessions and gets a new one via `Player::set_session`.

`src/main.rs` is a single large `getopts` setup (`get_setup()` → `Setup`) plus a `tokio::select!` main loop over discovery credentials, the spirc task, session errors, and signals. New CLI options mean touching the options table, `Setup`, and the usage text together.

## Fork-specific code

`src/server.rs` — `ApiServer`/`ApiServerTask`: a TCP control server configured by `ApiServerConfig` (`--api-bind`, default `0.0.0.0:50505`; `--api-allow`, a comma-separated CIDR allow list that is empty — i.e. unrestricted — by default; loopback is allowed unconditionally, listed or not, so a local client never has to be spelled out). It is spawned from `main()` before the connect loop and handed the `Spirc` and the `Session` via `set_session` on every (re)connect, since each connection gets a fresh pair. The two travel in one command so they can never end up belonging to different connections; the `Session` is there to fetch cover art with. `ApiServer::spawn` binds the listener before spawning, so port conflicts surface as `ApiServerError::Bind` instead of dying in the background; `shutdown()` drops the command channel to end the loop and awaits the task, and is spawned into the `JoinSet` in `main`'s shutdown path.

**It was UDP first, and the reasons it isn't any more are what most of the current shape follows from.** Datagrams meant a subscription had to be a lease clients renewed on a timer, a lost push left a client stale until the next re-sync, and a cover had to be split into MTU-sized chunks that nothing retransmitted — an oversized one simply never arrived. A stream removes all of that: the connection *is* the subscription, nothing is lost or reordered, and a picture goes out whole. Don't take that as an argument for adding a second transport back; it is an argument for not needing one.

The task is a `tokio::select!` loop over cancel-safe sources: the command channel, the cover channel, the player event stream, the AirPlay event stream, `listener.accept()`, and `conn_rx`. `handle_player_event` keeps the exposed state (track, volume, `PlaybackState`) and deliberately ends in a `_ => ()` arm so new upstream `PlayerEvent` variants don't break the build. Requests are `<command>[ <json payload>]` lines. Commands arriving before a session exists are logged and dropped.

**The loop never touches a socket.** An accepted connection is split: a reader task turns lines into `ConnectionEvent::Request` and reports `Closed` however the connection ends, and a writer task drains a bounded `mpsc` (`CONNECTION_QUEUE`, 16) and does all the waiting a slow client causes. The loop only ever `try_send`s. A full queue means the client stopped draining its socket, and `send_line` then drops the connection rather than waiting — on a stream there is no skipping one event and carrying on, since the client would hold a state that never becomes right again; closing the socket tells it so, and reconnecting gets a fresh snapshot. This is the one thing a stream costs that datagrams didn't, and it is why a stalled PC in another room cannot hold up the task that also serves the player.

`connections` is keyed by a `u64` from `next_connection_id`, not by peer address: a client that reconnects can land on the same ephemeral port, and its old connection's `Closed` would then arrive after the new one registered and unregister the live one. Dropping a `Connection` closes it — the queue's sender goes, the writer's loop ends, and its explicit `shutdown()` takes the socket down (the read half lives in the other task, so without that only half would close). `MAX_REQUEST_BYTES` (1024) bounds a request line, since a stream has no message boundary of its own and an unbounded `read_until` would let a peer decide how much this process buffers.

The allow list is checked once, in `admit`, when the connection is accepted — a peer that isn't welcome is refused and logged once instead of per message, which is the one thing this is cheaper at than datagrams were. Connection and subscription lifecycle are logged at `info`/`warn` with the peer address, so they show up without `RUST_LOG`; accepted commands the same way (`received '<command>' from <peer>`), now including `subscribe`/`unsubscribe`, which no longer arrive on a timer. Nothing about a rejected peer is retained anywhere — deliberate, on a closed LAN where a flood isn't a realistic concern. Don't reintroduce per-address bookkeeping on the untrusted path without asking.

**`subscribe` and `unsubscribe` are the whole client side.** Everything a subscriber needs is pushed, artwork included — nothing to poll, request, retry or correlate with a request. That is the point of the design and the thing to protect: if a change would make a subscriber send something to stay current, it is the wrong change. The query commands (`current_track`, `getvol`, `status`) serve a different audience — something that connects, asks one question and leaves — and a connection is not a subscription, so that is a legitimate way to use this. `subscribe` sets a flag on the connection and answers with a `snapshot`; `unsubscribe` clears it without closing anything. There is no lease, nothing to sweep, and no keepalive. Push payloads are the internally tagged `Event` enum (`snapshot`, `track_changed`, `playback_changed`, `volume_changed`, `cover`). Because `broadcast` takes `&mut self` — it may drop connections — while events borrow `&self.current_track`, events are serialized with `encode` before the call, hence `broadcast(Option<String>)` rather than a generic. `\n` is the frame boundary and `serde_json` escapes any newline inside a value, which `a_payload_never_contains_a_raw_newline` pins.

`PlaybackState` stores the last reported position plus a monotonic `Instant`, and `position_ms()` extrapolates forward while playing (capped at the track duration). Positions therefore go out valid *as of the moment of sending*, so clients extrapolate against their own clock and never need clock agreement with this machine — relevant since the fork runs headless on a different host than its clients.

`TrackResponse` (the `current_track` answer, and the `track` field of events) is built by `From<AudioItem>` for Spotify and filled field by field from DMAP for AirPlay, into one flat shape either way — tracks report their artists and album, episodes fall back to the show name, local files to their tags. Every field is always present, empty rather than omitted, so clients can rely on the shape; an ended session publishes an empty one (`clear_now_playing`) rather than leaving the last track visible forever.

**A cover is pushed to subscribers as its own `cover` event, carrying the whole picture** — never as a url, since the clients are PCs on a LAN that must never reach the internet; only the Pi does. It is a separate event rather than a field on `track_changed` because the picture is not there yet when the track changes: it is fetched, which takes a few hundred ms, and folding it in would mean holding the track event back for it. An earlier design did exactly that and it was wrong twice over — it also made that datagram exceed what one can hold, with a real sender's ~180 kB artwork. So `track_changed` goes out at once and means "forget the old artwork"; a `cover` follows if there is one. Every path that produces a picture ends in `announce_cover`: a fetch landing, a **cache hit** (`load_cover` — setting the field and telling nobody left a skip-back showing nothing), an AirPlay push, and a fresh `subscribe` while something is already playing. Spotify's *largest* cover is the one fetched.

That line is the longest thing this server can send, and its bound is a **published property** rather than something clients guess at: `MAX_COVER_BYTES` (2 MB) grown by base64 and wrapped in JSON comes to under 2.8 MB, which is the figure the module docs and `contrib/api_test.py` both state and `the_longest_line_is_bounded` pins. That is the second job `MAX_COVER_BYTES` does now that no datagram has to hold a picture — the first being the only bound on memory against an AirPlay sender, which pushes artwork over DMAP and is believed. Without a cap on what is accepted there is no figure to hand a client, and "read until newline" has no safe implementation. Don't remove it on the grounds that TCP doesn't need it.

**There is no `cover` command and no `pending` flag; both were deleted rather than kept for symmetry.** Asking for a picture made a client hold request state and tell an answer from an event, and a *negative* answer then had to distinguish "no cover" from "not yet" — which is the only thing `pending` ever existed for. Under a push none of it is reachable: `load_cover` clears `current_cover` first, so a track without artwork, one whose fetch failed and one still fetching are all simply quiet, and a client that draws nothing from `track_changed` until a `cover` arrives is right in all three. `Event::Cover` therefore only ever goes out carrying a picture, and `encode_cover` returns `None` when there isn't one rather than inventing an empty event. If you find yourself adding a way to ask, or a flag saying why nothing came, re-read this paragraph. `announce_cover` also skips the encode entirely when nobody is subscribed, since that is the one expensive thing this task does and a track change reaches it either way.

**Nothing re-encodes a picture, and there is deliberately no code that could.** A cover is held and sent exactly as it arrived, up to `MAX_COVER_BYTES` (2 MB), which is the only bound left. There was a `shrink_cover` re-encoding anything over 256 kB down to 640 px of JPEG; it existed because UDP could not deliver iTunes on Windows pushing 1.4 MB of PNG, and on a stream that is a file transfer that takes a fraction of a second on a LAN. It cost the one thing a client actually notices, so it went — and the `image` dependency with it, since that was its only user. `load_airplay_cover` went the same way: it existed only to move a shrink off the loop, and a pushed cover is now simply `announce_cover`d. Don't reintroduce any of this to save bytes without asking; the whole point of the TCP move was that bytes stopped being the constraint.

`fetch_cover` runs off the task's loop (`tokio::spawn`, reporting back over a second channel that the task owns both ends of — the loop still ends on `cmd_rx` closing). It is the only producer of `CoverFetched`, which is why `url` is a plain `String`: a cover from an AirPlay sender was pushed rather than fetched and never travels this way. `CoverCache` keeps the last `COVER_CACHE_SIZE` covers so skipping back and forth doesn't refetch. There is deliberately no fallback: too big (`MAX_COVER_BYTES`), too slow (`COVER_FETCH_TIMEOUT`), no session yet, or a failed fetch all mean `bytes: 0`, which clients must handle regardless. The tests seed `CoverCache` instead of fetching, so they stay small and portable.

`contrib/api_test.py` is the reference client and doubles as the wire-format documentation: it connects, subscribes, reads lines, reconnects when the connection goes and forwards typed commands. Keep it in step with the protocol.

Its docstring opens with the shape of a client — connect and `subscribe`, loop reading lines, reconnect — and with the warning that matters most for the Delphi port this exists to feed: **the read loop blocks, so in a GUI it belongs on a worker thread**, with events handed to the UI thread rather than widgets touched from the reader. A console program like this one can read on the main thread and put stdin on the background one; a VCL app must do the opposite or the window freezes for as long as nothing arrives, which is most of the time.

Its `LineReader` is written the long way — `recv` into a buffer, find `\n`, cut, loop over the buffer rather than one line per read — deliberately, and the docstring says why: it is the algorithm a client in any language has to implement, and every ready-made line reader hides both its own length limit (Indy's `MaxLineLength` is 16 kB, and `maSplit` silently hands you half a message) and what a timeout means. The timeout rule is the part worth keeping straight: **a read timeout on an empty buffer is not an error** — this server is silent while nothing happens — while one holding a partial line is a stall, since the rest was promised. Two other things there are load-bearing: `Remote` is one long-lived sender bound to whichever connection is current, rather than a thread per connection (on reconnect the previous one would sit on the same queue stealing every other command), and *everything* the client sends goes through it, since two `sendall`s racing can interleave and deliver half a command inside another.

The client also probes with `status` after 30s of quiet and gives up if no answer comes in 10s. That is a client-side choice with no server-side counterpart — no lease came back — but it is the only way to notice a peer that vanished without closing the socket (the Pi losing power, Wi-Fi dropping), which TCP alone reports only after the kernel's own keepalive gets round to it, hours later.

The module's `tests` cover the response shapes, position extrapolation, CIDR matching, `admit`'s allow-list decision, the backpressure drop, and — via `TestServer`, which runs a real task on a loopback port and talks to it over a real connection — the push path end to end. Keep them in step when changing the wire format.

`Spirc` carries a fork-local `#[derive(Clone)]` (`connect/src/spirc.rs`) so the server task can hold its own handle — keep that in mind when merging upstream.

### AirPlay (`airplay/`)

An AirPlay receiver that runs alongside Spotify Connect, shares the same device name (`-n`) and reports through the same control API. On by default (`airplay-remote-control` is in the root `default` features and in `RPI_FEATURES`); `airplay` alone gives the receiver without remote control, `airplay-dns-sd` swaps the mDNS backend.

**It implements classic AirPlay (AirPlay 1 / RAOP), and that is the whole design.** The crate did once implement AirPlay 2 — pairing, encrypted RTSP, FairPlay key unwrapping, the lot — and against a real iPhone it worked: it paired, streamed and played. It also offered *no way whatsoever to control the phone*, because an AirPlay 2 sender sends no `DACP-ID`/`Active-Remote` and exposes no remote-control channel to a receiver. That is unsolved in every open implementation, shairport-sync included. A sender that finds only a `_raop._tcp` advertisement falls back to the classic path, where it puts those two headers on every request — and that is what makes pause, resume, next and volume possible at all. So `discovery` advertises exactly one service with a classic TXT record: **adding an `_airplay._tcp` registration, or a `features`/`pk` field, silently costs all remote control.** All the AirPlay 2 code was deleted, taking the GPLv2-licensed FairPlay port with it; the tree is MIT throughout again, which matters because `rpi-release.yml` publishes the binary.

Layout: `discovery` (mDNS, libmdns or dns-sd) → `rtsp` (`connection.rs` drives one plaintext TCP connection, `mod.rs` dispatches `OPTIONS`/`ANNOUNCE`/`SETUP`/`RECORD`/`FLUSH`/`TEARDOWN`/`SET_PARAMETER`/`GET_PARAMETER`, `message.rs` parses) → `legacy` (`ANNOUNCE` negotiation, AES-128-CBC decrypt, the RTP receive loop; `rsa_key.rs`, `sdp.rs`) → `codec` (ALAC via Symphonia) → `sink` (its own `Box<dyn Sink>`, the same backend/device/format Spotify uses but a separate instance — nothing arbitrates between the two). `dacp.rs` is the control channel back to the sender, `dmap.rs` parses the metadata/artwork/progress it pushes, `device_id.rs` derives this receiver's six identity bytes.

Two things a sender demands before it will stream: an `Apple-Response` to its `Apple-Challenge` (`rtsp::apple_challenge`, RSA PKCS#1 v1.5 **unprefixed** over challenge + local IP + device id), and a `GET_PARAMETER` volume answer. The RSA key in `legacy/rsa_key.rs` is the long-published AirPort key every open RAOP implementation embeds, not a secret of this deployment.

`device_id.rs` derives the identity from the device name's SHA-1 rather than a MAC or a file: `-n` already names this device, so the identity is stable across restarts with nothing to persist and nothing to configure. This is why there is no `--airplay-identity-store`.

Control flows back over DACP: `GET /ctrl-int/1/<command>` with only `Host` and `Active-Remote` headers, to the endpoint found by resolving the sender's `DACP-ID` over mDNS. `src/server.rs`'s `Source` decides which source a command reaches — `control()`/`set_volume()` route to spirc or to DACP — and `airplay_is_on_the_air` keeps an abandoned session from writing over live state. `Source` means "whichever source last *played*", moved only by a positive now-playing signal: both the endpoint and the routing deliberately survive `SessionEnded`, since `resume` is the only way to tell a stopped sender to play again. Handing control back to spirc on `TEARDOWN` — which an earlier version did whenever a Spotify session existed, i.e. always on the Pi — is exactly what made `resume` unable to restart a paused phone: the command went to a spirc with nothing loaded.

**Not every sender that offers control can be reached over DACP.** Apple Music on Windows sends `DACP-ID`/`Active-Remote` like any classic sender, but its `iTunes_Ctrl_<id>._dacp._tcp` advertisement never resolves — `dacp::resolve_port` times out and `next`/`pause`/`resume` had nowhere to go at all. So `control()` falls back to forwarding the command verbatim to a helper on the sender's *own* machine, which controls the player locally and needs no mDNS: `contrib/airplay-control-windows.ps1` (SMTC for transport, `IAudioEndpointVolume` for volume). That forward goes out as a UDP datagram from `helper_socket` — the one datagram left in this file, since the helper is a small script that listens for one, and nothing reads the reply. The address comes from `AirplayEvent::SessionStarted`, which carries the RTSP peer and therefore exists for every sender, resolved or not — that is what it is for, and why it is separate from `DacpAvailable`. DACP is still tried first: it is the sender's own protocol and needs nothing installed at the far end. Only transport is forwarded — volume already works, via the sender's `SET_PARAMETER` push inbound and the receiver's own attenuation outbound — and `--airplay-helper-port 0` turns the whole fallback off. Note this does not make AirPlay 2 worth revisiting: control there runs over this same DACP mechanism, so the broken step would be identical.

Everything here matches shairport-sync's actual source (fetched and read), not community spec documents — several defects came from trusting the latter. Keep it that way.

`contrib/ci-local.sh` runs the same checks locally. Note what it cannot do: `alsa-backend` only builds on Linux, so on macOS the clippy pass over the shipped feature set needs Docker (it shells out to `cross`) and the script exits non-zero when neither is available, rather than reporting a green run that skipped it. That gap is real — code behind `#[cfg(feature = "alsa-backend")]` is invisible to a plain `cargo clippy` on macOS, which is how an upstream `useless_borrows_in_formatting` in `main.rs` reached CI unnoticed.

`.github/workflows/pipeline.yml` — fork-local CI entry point for `API`, and the only workflow that fires on that branch. Two jobs in parallel (`quality`: fmt + clippy on default features and on the shipped set; `test`: `cargo test --workspace`), then `rpi-release` gated on both. It does **not** call upstream's `quality.yml`/`build.yml`/`cross-compile.yml`: their Windows/MSRV/`cargo hack --each-feature` fan-out costs tens of minutes per commit for coverage this fork does not use — one binary, one Pi, one feature set. Those files are untouched and still run on `dev`/`master` and pull requests, which is where the wide coverage belongs (e.g. after an upstream merge). Upstream's `prepare-release.yml` and `release.yml` (crates.io publishing) were deleted as irrelevant to the fork — expect them back on the next upstream merge.

`.github/workflows/rpi-release.yml` + `contrib/rpi-update.sh` — fork-local delivery to the Raspberry Pi that runs this build. The last pipeline stage cross-compiles `aarch64-unknown-linux-gnu` (via the existing `Cross.toml`) with `rustls-tls-native-roots,alsa-backend,with-libmdns,airplay-remote-control` and publishes the stripped binary — uncompressed, as the single asset `librespot-aarch64` — as a release tagged with the build version and marked `--latest`. The stable download URL is therefore `/releases/latest/download/librespot-aarch64`, which GitHub redirects to whichever release is newest. An earlier design reused one rolling tag (`api-latest`, deleted and recreated per build); the repository has **immutable releases** enabled, which rejects a reused tag outright, so nothing here may delete or overwrite a release — every build must bring a new tag. That also means tag creation has to stay permitted for `GITHUB_TOKEN`; a ruleset restricting ref creation blocks the whole workflow. A fixed asset name means the download URL is stable, which is the whole point: `contrib/rpi-update.sh` is deliberately three commands — `curl`, `install` into `/usr/bin/librespot` (the path in the unit's `ExecStart`), and a `systemctl restart` — and nothing more: no unpacking, no checksum, no fallbacks. Keep it that way. `rustls` rather than `native-tls` on purpose: the cross image's OpenSSL does not match the Pi's, so the artifact would not start. Unlike the other workflows this one does not set `-D warnings` — it ships an artifact, and a new lint should not block a deploy. Its env vars are all `RPI_`-prefixed: workflow-level env is visible to every action, and a bare `TAG` was picked up by the ubi installer inside `actions-rust-cross`, which then tried to download a release of its own named `api-latest`. Don't un-prefix them. `Swatinem/rust-cache` is keyed by the target here so the cross artifacts don't share a cache with the host-side jobs.

Builds are versioned `year.month.day[.n]` — `26.8.8` for the first build of a day, `26.8.8.1` for the second, and so on (upstream's `SEMVER` never moves, and `BUILD_ID` is random, so neither identifies a build). The workflow derives it by counting existing git tags for today, hence the `fetch-depth: 0` checkout; the tag itself is created by `gh release create` (pinned to the built commit with `--target`), which happens last, so a failed build leaves no gap in the sequence. The version reaches the binary as `LIBRESPOT_BUILD_VERSION`, read by `option_env!` in `get_version_string` (`src/main.rs`) and forwarded into the container by the fork-local `[build.env] passthrough` in `Cross.toml` — without that entry `cross` drops it and every build silently loses its version. Local builds have no such env var and print the plain upstream string. These are fork infrastructure and deliberately get no `CHANGELOG.md` entry.
